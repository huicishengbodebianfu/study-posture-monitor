| 序号 | 模型 | 网关 | 超时 | 角色 |

## 四、可靠性机制（6 项全在）

| 机制 | 位置 | 行为 |
|---|---|---|
| 能力探测 | `VisionPool.probe()` | 启动查 `/models` 确认模型在目录里，逐后端打日志 |
| 指数退避 | `_backoff()` | 0.8 → 1.6 → 3.2 s，叠加抖动 |
| 超时降级 | `analyze` 的 Timeout 分支 | 按失败处理，不写缓存 → 回退快速通道 |
| 429 切后端 | `SWITCH_CODES` | 429/5xx 立即换下一台，绝不原地重试 |
| 故障切换 | `CircuitBreaker` + EWMA 选路 | 连续 3 次失败熔断 120 s；备用按实测速度挑最快的 |
| 坏例落盘 | `BadcaseStore` | 失败时存 `JSON(后端/HTTP码/错误) + 原图`，按天分目录 |

附加：**并发投票**、**启动测速**、**TTL 防陈旧**、**should_alert 门控**（模型说"正常低头"就不翻案）。

## 五、数据契约

提示词要求模型只输出一个 JSON（638 字符提示词，10 字段）：
`state / upright / confidence / person_count / scene / posture_hint / object_hint / evidence / should_alert / needs_review`

服务端 `schema.normalize()` 做四件事：剥 markdown 包裹 → 字段别名映射 → 枚举白名单过滤 → 类型强转与范围裁剪。
**任何垃圾输入都产出合法结果**，绝不抛异常。翻案条件是唯一收口点：

```
should_alert(state, upright, conf, model_alert, min_conf=0.6):
    模型说不提醒 → 不提醒
    state 不在 {slouch, lean, phone, daze} → 不提醒   # sleep/away 只记录
    upright 不是 False → 不提醒
    conf < 0.6 → 不提醒
```

## 七、已知问题

1. **双票率低（5/36）**
   并发 2 路，但第二台经常在 15 s 内回不来 → 退化为单票。根因是 discovery-api 动态限速 + 延迟抖动，
   不是选路逻辑。想提高双票率：调大 `AI_PARALLEL_DEADLINE`（18 s 仍 < 30 s），或换更稳的备用。

2. **坏例堆积 314 个**
   是今天反复调参留下的。`BadcaseStore` 每目录上限 500 对，到量会删最旧，不会撑爆磁盘，但建议清一次。

3. **三个网关的行为差异大**
   同一个 `intern-s2`：discovery-api 要 ~30 s，魔搭只要 3.6 s。选备用时必须按实测速度而不是按模型名。

4. **快速通道仍是老问题**
   阈值 0.37/0.03 是阶段一机位标定的，换网图/机身倾斜会误判。慢通道不能推翻快速通道的"不端正"（融合表单向）。

5. **魔搭令牌是写权限**
   存在服务器 `.env` 里。建议换只读令牌。
