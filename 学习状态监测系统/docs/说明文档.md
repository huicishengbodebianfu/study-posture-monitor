## 1. 两条通道的设计

系统的判定能力被拆成两个**独立、可分别替换**的通道：

| | 快速通道 | 慢速通道 |
|---|---|---|
| 实现 | 本地 YOLOv8-pose（OpenVINO） | Qwen-VL + DeepSeek |
| 延迟 | 60~150 ms | 秒级 |
| 成本 | 0（服务器已有） | 按 token 计费 |
| 能力 | 骨骼几何：低头/驼背/侧歪 | 语义：玩手机、发呆、离开 |
| 频率 | 每帧（10s） | 每 30s 抽查 |
| 默认 | **开启** | **关闭**（`MULTIMODAL_ENABLED=false`） |

**为什么不全用视觉大模型？**
0.1 fps 的场景下大模型并非不可行，但每帧几百毫秒到数秒的延迟 + 持续计费，
对"只是看坐没坐直"这件事是浪费。几何姿态既快又免费，足够覆盖阶段一目标。

**为什么保留慢速通道？**
阶段二要判"在干什么"，几何信息不够。接口先留好，开关一开即可接入，
不必重构主链路。

## 2. 云端推理管线

入口：`cloud/app.py` 的 `detect()`。共 5 步。

### 2.1 预处理 `preprocess()`

```python
arr  = np.frombuffer(image_bytes, np.uint8)
img  = cv2.imdecode(arr, IMREAD_COLOR)        # 解码 JPEG
scale = min(640/w, 640/h)                      # 等比缩放
resized = cv2.resize(img, (new_w, new_h))
canvas = np.full((640,640,3), 114)             # letterbox 灰边
canvas[pad_y:..., pad_x:...] = resized
rgb  = cvtColor(BGR2RGB) / 255.0
blob = transpose(rgb, (2,0,1))[None]           # (1,3,640,640)
```

**为什么用 114 填充？** YOLO 训练时的标准 letterbox 灰边值，保持推理分布一致。
**为什么记录 scale/pad？** 关键点是在 640×640 画布上算的，必须还原回原图坐标才能算真实比例。

### 2.2 推理 `infer()`

```python
pred = model([blob])[0][0]      # shape (56, 8400)
scores = pred[4, :]             # 第 5 行 = 该 anchor 的人体置信度
best = argmax(scores)
if scores[best] < CONF_THRESHOLD: return None, None
kp = pred[5:, best].reshape(17, 3)   # 17 点 × (x, y, conf)
```

**56 是怎么来的？** `4`（cx, cy, w, h）+ `1`（置信度）+ `17×3`（关键点 x/y/conf）= 56。
**8400 是什么？** 640/8、/16、/32 三个尺度下 anchor 点总数 = 80²+40²+20² = 8400。

> ⚠️ 当前实现**只取置信度最高的一个 anchor，没有 NMS**。
> 这建立在"D1：单人固定用户"的假设上。画面里出现第二个人时，结果不可预期。

### 2.3 坐标还原 `unletterbox()`

```
x_orig = (x_canvas − pad_x) / scale
y_orig = (y_canvas − pad_y) / scale
```

### 2.4 特征提取 `posture.extract_features()`

```python
NOSE, L_SHOULDER, R_SHOULDER = 0, 5, 6
if any(kp_conf[i] < 0.5 for i in (0,5,6)):  → invalid("low_kp_conf")

shoulder_width = |x_ls − x_rs|           # 像素
if shoulder_width < 1e-6:                → invalid("bad_shoulder_width")

head_height    = ((y_ls + y_rs)/2 − y_nose) / shoulder_width
shoulder_level = |y_ls − y_rs| / shoulder_width
```

**关键点：归一化用的是"肩宽"，不是图像宽高。**

这意味着：
- 数值**不是 0~1 的比例**，而是"头高是肩宽的多少倍"
- 相机拉远拉近、分辨率变化，数值基本不变（尺度不变性）
- 所以它可以大于 1（理论上头很高时）

例：坐直 `head_height ≈ 0.68`，驼背 `≈ 0.21`。

> 旧文档写"归一化到 0~1"是不准确的表述，容易让人误判数值含义。

**为什么必须显式 `float()`？**
OpenVINO 输出是 `numpy.float32`。`round(np.float32)` 仍返回 `np.float32`，
而 `json.dumps` 不认 numpy 标量 → FastAPI 直接 500。这是本项目最致命的原始 bug，
详见 §7.1。

### 2.5 判定 `is_upright()`

```python
if not features.valid:        return None          # 无法判定
if head_height < MIN:         return False         # 低头/驼背
if shoulder_level > MAX:      return False         # 侧歪
return True
```

注意**短路顺序**：先判头高再判肩平差。两个条件不会同时被报告，
`reason` 只保留第一个命中的原因（快速通道里其实是固定 `fast_path_bad`）。

## 3. 姿态特征与阈值

### 3.1 几何含义

```
        鼻(0)
         ●            head_height = 肩中点Y − 鼻Y（除以肩宽）
        / \
       /   \
  左肩(5)---右肩(6)     shoulder_level = |左肩Y − 右肩Y|（除以肩宽）
```

- **低头/驼背** → 鼻子往下掉 → `head_height` 变小 → 低于阈值即判不端正
- **侧歪/歪头** → 两肩不等高 → `shoulder_level` 变大 → 高于阈值即判不端正
- **人走开/太暗** → 关键点置信度不够 → `valid=False` → 不判

### 3.2 阈值为什么是 0.37 / 0.03

| 样本 | head_height | shoulder_level |
|---|---|---|
| 自然坐直（9-25 标定） | 0.6798 | 0.0050 |
| 刻意驼背（9-25 标定） | 0.2067 | 0.0065 |

按"取两组中位"的原则：
- `HEAD_HEIGHT_MIN = (0.6798 + 0.2067)/2 ≈ 0.44`，实际取**偏松一档 0.37**（先松后紧）
- `SHOULDER_LEVEL_MAX` 的标定**失败了**：两组几乎没差别（0.0050 vs 0.0065），
  0.03 是兜底取值

### 3.3 侧歪阈值为什么不可靠

2026-10-08 的实测日志里，驼背帧的 `shoulder_level` 达到 **0.286~0.334**，
是阈值的 10 倍。说明：

1. 人一歪头/转肩，肩平差会剧烈变化，0.03 这个阈值对侧歪其实**很敏感**
2. 但 9-25 标定样本里没有真正的侧歪动作，导致当时误以为"区分度小"
3. 结论：**需要用真实侧歪样本重新标定**，否则可能"轻微倾斜就吹"

## 4. 规则引擎

`posture.RuleEngine`，20 行，但决定了体验。

```python
class RuleEngine:
    consecutive_frames = 2
    dedup_seconds      = 60
    _bad_streak = 0
    _last_blow_ts = 0.0

    def update(upright):
        if upright is None:            # 无法判定
            _bad_streak = 0
            return "none"
        if upright:                    # 端正
            _bad_streak = 0
            return "none"
        _bad_streak += 1               # 不端正
        if _bad_streak >= 2 and now - _last_blow_ts >= 60:
            _last_blow_ts = now
            _bad_streak = 0            # 触发后清零
            return "blow"
        return "none"
```

### 4.1 四个设计点

| 设计 | 效果 |
|---|---|
| 连续 2 帧才吹 | 偶然低头捡笔不会触发，约 20 秒确认 |
| 60 秒去重 | 持续驼背时每 60 秒提醒一次，不是每 10 秒 |
| 端正立即清零 | 坐直马上停，不会"记仇" |
| `None` 也清零 | 人走开/太暗会打断连续计数，避免回来后立刻被吹 |

### 4.2 边界行为

- **触发后 `_bad_streak=0`**：已触发过一次后，即使继续不端正，也要等 60 秒去重窗口结束才会再吹（不是每 20 秒）
- **去重窗口未到时不重置 streak**：streak 会继续增长，窗口一过下一帧立刻触发
- **进程重启计数清零**：所以 `--workers 1` 是硬要求（多进程会各算各的）
- **多客户端共享**：手机标定工具和 ESP32 用同一把 key，会互相打断计数

## 5. 多态检测与融合

### 5.1 编排器 `MultimodalDetector`

```
should_run() = enabled AND qwen.enabled AND deepseek.enabled AND 距上次 ≥ 30s
run_async()  → 起 daemon 线程（不阻塞 HTTP 响应）
_run()       → Qwen 看图 → DeepSeek 决策 → 存 _last_result
fuse()       → 主线程读 _last_result，与快速通道结果合并
```

**线程模型**：主线程只读 `_last_result`（加锁），慢速线程写。
慢速线程失败只记日志，不影响主链路 → **静默降级**。

### 5.2 两个 AI 的分工

| | AI-1 | AI-2 |
|---|---|---|
| 模型 | `qwen-vl-plus`（DashScope 兼容模式） | `deepseek-chat` |
| 输入 | JPEG（base64 data URL）+ 固定提示词 | 结构化视觉描述 + 最近 5 条状态 |
| 输出 | `{person_present, person_count, scene, posture_hint, object_hint}` | `{state, upright, should_alert, confidence, reason}` |
| 温度 | 0.1 | 0.1 |
| 容错 | 剥离 markdown 代码块 → 截取 `{...}` → 解析 | 同左；`state` 非法则置 unknown |

**为什么拆两个模型？**
视觉模型看图强、文本模型推理强；拆开后任一方可独立替换，
也便于分别计费与限流。

### 5.3 融合优先级

`fuse(fast_upright, fast_reason)` 按顺序短路：

| 顺序 | 条件 | 结果 | source |
|---|---|---|---|
| 1 | 快速通道明确 `False` | 不端正 | `fast` |
| 2 | 慢速结果 `upright=False` | 不端正（慢速可"翻案"） | `slow` |
| 3 | 快速通道明确 `True` | 端正 | `fast` |
| 4 | 慢速结果 `upright=True` | 端正 | `slow` |
| 5 | 其余 | 无法判定 | `fused` |

> ⚠️ **实现与文档不一致**：`cloud/README.md` §11.5 说"慢速结果有缓存有效期，
> 过期后回退到快速通道"，但代码里 `latest()` **没有 TTL**。
> 只要慢速通道曾判定不端正，这个结论会一直参与融合，直到下一次慢速结果覆盖。
> 实际影响：慢速通道开启时，一次"玩手机"判定可能长时间持续触发提醒。
> 修复方式：给 `MultimodalResult` 加时间戳，`fuse()` 里判断是否超过 N 秒。

### 5.4 关闭时的行为

`MULTIMODAL_ENABLED=false` 时：
- `ready=False` → `should_run()` 恒 False → 永不启动慢速线程
- `latest()` 恒 None
- `fuse()` 退化为"直接返回快速通道结果"
- 只有快速通道也判不出时，才返回 `source="fused", state="unknown"`

这正是线上当前状态。

## 6. 固件状态机

### 6.1 三态（当前实际只有两态在跑）

```
            ┌──────────────┐
            │    NORMAL    │ 每 10s 拍照上传；风扇停；LED 灭
            └──────┬───────┘
      收到 blow    │
                   ▼
            ┌──────────────┐
            │   BLOWING    │ 风扇 255；LED 亮
            └──────┬───────┘
             5 秒到 │
                   └──▶ NORMAL

            ┌──────────────┐
            │    SNOOZE    │ 不上传；LED 亮
            └──────────────┘
             ↑ 仅当 BUTTON_ENABLED=1 才可达
```

> ⚠️ `BUTTON_ENABLED = 0`，`handleButton()` 整段被 `#if` 编译掉，
> `enterSnooze()` 实际**不可达**。SNOOZE 是保留能力，不是当前功能。

### 6.2 非阻塞怎么做到

所有定时都是 `millis()` 差值，没有 `delay()`：

```cpp
case STATE_NORMAL:
  if (now - g_lastUploadMs >= UPLOAD_INTERVAL_MS) { ... }   // 10000
case STATE_BLOWING:
  if (now - g_blowStartMs >= BLOW_DURATION_MS) enterNormal(); // 5000
```

`millis()` 约 49.7 天回绕，但用**无符号相减**能正确处理回绕。

### 6.3 外设通道分配

| 外设 | 资源 | 说明 |
|---|---|---|
| 风扇 | LEDC channel **0**，5 kHz，8 bit | `ledcAttachChannel(PIN_FAN, 5000, 8, 0)` |
| 摄像头 XCLK | LEDC channel **1** | `config.ledc_channel = LEDC_CHANNEL_1` |
| 红灯 | 普通 GPIO 推挽 | `digitalWrite` |

ESP32 core 3.x 移除了 `ledcSetup/ledcAttachPin`，必须用 `ledcAttachChannel` 显式占通道，
且 `ledcWrite` 的第一个参数从"通道"变成"引脚"。这是 2.x→3.x 的破坏性变更。

### 6.4 摄像头初始化

```cpp
camera_config_t config = {};   // 必须零初始化！
```

不写 `= {}` 时 `fb_location` 等字段是栈上的随机值，表现为"有时能初始化、有时报错"。

**PSRAM 分支**：

| 条件 | frame_size | quality | fb_count | 位置 |
|---|---|---|---|---|
| 有 PSRAM | VGA | 12 | 2 | PSRAM |
| 无 PSRAM | SVGA | 15 | 1 | DRAM |

**OV3660 处理**（关键）：

```cpp
if (s->id.PID == OV3660_PID) {
  s->set_vflip(s, 1);        // 翻转回来
  s->set_brightness(s, 1);
  s->set_saturation(s, -2);
}
```

OV3660 默认输出上下颠倒。若不翻转，`head_height = 肩Y − 鼻Y` 会变成负数，
**坐直也被判成驼背**，导致每 60 秒吹一次。这是实测踩到的坑。

### 6.5 上传与解析

```cpp
http.begin(SERVER_URL);
http.setTimeout(8000);
http.addHeader("Content-Type", "image/jpeg");
http.addHeader("X-Device-Key", DEVICE_KEY);
code = http.POST(fb->buf, fb->len);      // 二进制直发，无 multipart
```

成功后：

```cpp
JsonDocument doc;                         // v7 动态分配
const char *action = doc["action"] | "none";
if (strcmp(action, "blow") == 0) enterBlowing();
```

**固件只认 `action`**。云端新增 `state`/`source`/`head_height` 等字段不影响固件，
这是刻意的前向兼容设计。

### 6.6 调试接口 `/capture`

ESP32 自己在 80 端口起了一个 WebServer，`GET /capture` 返回当前帧 JPEG。
用于"不经过云端"直接看摄像头画面。

> 限制：HTTP 上传是**阻塞**的（最长 8 秒超时），这段时间 `loop()` 卡在 `http.POST()`，
> `webServer.handleClient()` 不被调用，`/capture` 会无响应。所以它是调试工具，
> 不适合当视频流用。

## 7. 关键 bug 复盘

### 7.1 numpy float32 无法 JSON 序列化（致命，已修）

**现象**：`POST /detect` 稳定 500，日志
`TypeError: Object of type float32 is not JSON serializable`。

**根因**：关键点来自 OpenVINO，类型是 `np.float32`；算术结果仍是 `np.float32`；
`round()` 对 `np.float32` 返回的仍是 `np.float32`；`json.dumps` 只认 Python 原生类型。

**修复**：`posture.py` 里 `float(head_height / shoulder_width)` 显式转换；
`app.py` 返回前再 `round(float(...), 4)` 双保险；`ai_providers.py` 的 `confidence` 同样处理。

**教训**：numpy 标量会一路"污染"到序列化层，边界处必须显式转型。

### 7.2 systemd 要求不存在的用户（服务起不来）

**现象**：`Failed to determine user credentials`，服务直接退出。

**根因**：单元文件写 `User=posture`，但项目里从未创建该用户。

**修复**：改 `User=root` / `Group=root`。

### 7.3 `.env` 不被读取（改配置无效）

**现象**：改了 `.env` 里的阈值和密钥，重启服务毫无变化。

**根因**：单元文件只有硬编码的 `Environment=` 行，没有 `EnvironmentFile=`。

**修复**：加 `EnvironmentFile=/opt/posture/.env`。

### 7.4 GPIO0 当按钮 → 误触发 5 分钟免打扰

**现象**：设备周期性"失联"5 分钟，之后自己恢复。

**根因**：GPIO0 同时是摄像头 **XCLK（20 MHz 时钟输出）**。把它配成 `INPUT_PULLUP` 后，
摄像头时钟被读取为"按键按下" → 进入 SNOOZE → 停止上传 5 分钟。

**修复**：`BUTTON_ENABLED 0`，默认关闭免打扰。要恢复必须换空闲脚（如 GPIO15）。

### 7.5 GPIO12 与 microSD 共用

**现象**：风扇引脚行为异常。

**根因**：GPIO12 是启动配置脚 MTDI，且与板载 microSD 共用。

**修复**：风扇改 GPIO13，红灯改 GPIO14。

### 7.6 `ledcSetup/ledcAttachPin` 在 core 3.x 被移除

**现象**：编译报错，函数不存在。

**修复**：`ledcAttachChannel(pin, freq, res, channel)`，`ledcWrite(pin, duty)`。
**代价**：固件**必须**用 ESP32 core 3.x 编译，2.0.x 编不过。

### 7.7 `StaticJsonDocument<256>` 容量风险

**现象**：旧文档/旧代码用固定 256 字节缓冲。

**风险**：线上响应已含 `state`/`source`，叠加慢速通道较长的 `reason` 文本，
256 字节有溢出风险（溢出后 JSON 解析失败，动作为 none，表现为"该吹不吹"）。

**修复**：改 `JsonDocument`（v7 动态分配），容量随内容增长。

### 7.8 摄像头配置未零初始化

**现象**：摄像头初始化偶发失败，重启又好了。

**根因**：`camera_config_t config;` 未初始化，`fb_location` 等字段是栈垃圾。

**修复**：`camera_config_t config = {};`。

## 9. 安全模型

| 层 | 措施 | 局限 |
|---|---|---|
| 传输 | 无 | **明文 HTTP**，公网可嗅探 |
| 鉴权 | `X-Device-Key` 头校验，不匹配 401 | 密钥硬编码在固件与 `.env`；曾出现在对话记录 |
| 数据留存 | 云端**不落盘、不建库**，帧处理完即弃 | 日志会记录数值（不含图像） |
| 图像隐私 | 已接受上云 | 无端到端加密 |
| 服务器 | ufw 仅放行 22/8000；root 密钥登录 | **root 密码登录开启**，存在爆破风险 |

**改进建议**（按性价比排序）：

1. 服务器 `PermitRootLogin prohibit-password`（零成本，立刻见效）
2. 轮换 `DEVICE_KEY`，并改为从环境变量注入（而非硬编码）
3. 上 HTTPS（需要域名 + 证书；或直接用反向代理）
4. 加 IP 白名单 / 请求频率限制
5. 固件里不要把 WiFi 密码和密钥写死后分享

## 11. 调试与观测手段

| 手段 | 命令 / 位置 | 用途 |
|---|---|---|
| 云端实时日志 | `journalctl -u posture -f` | 看每帧的 head_height/判定/action |
| 只看判定行 | `journalctl -u posture -f \| grep head_height` | 排除噪声 |
| 确认阈值加载 | `journalctl -u posture \| grep "startup, thresholds"` | 验证 `.env` 生效 |
| 健康检查 | `curl http://IP:8000/health` | 服务存活 |
| 单帧手测 | `curl -X POST ... --data-binary @x.jpg` | 排除固件问题 |
| 固件串口 | 115200 | WiFi、CAM、HTTP、状态迁移 |
| 固件直连抓图 | `http://<ESP32-IP>/capture` | 验证摄像头（不经云端） |
| 手机标定 | `python tools/capture_server.py` | 实时看特征值，无需硬件 |
| 设备在线探测 | `ping` + 服务器帧计数 | 排查丢帧 |

### 一条命令定位"该吹不吹"

```bash
# 1) 云端是否收到帧、判定是什么
journalctl -u posture -f | grep -E "head_height|bad device key"

# 2) 固件是否收到响应
# 串口应打印：[HTTP] resp: {"action":"..."}

# 3) 若云端 blow 但风扇不转 → 硬件（GPIO13 / S8050 / 5V）
# 4) 若云端一直 none 且 head_height 正常 → 阈值或规则计数
```
