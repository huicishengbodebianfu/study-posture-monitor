## 1. 项目是什么

一个**单人使用的坐姿监测小装置**：桌面上方的摄像头每 10 秒拍一张照，上传云端；
云端用 AI 找出人体关键点，判断有没有低头、驼背、侧歪；判定为不端正时，
桌面上的小风扇对着手吹 5 秒，同时亮红灯。

### 1.1 目标

| 目标 | 说明 |
|---|---|
| 可靠识别坐姿 | 只判定"坐姿是否端正"，不做身份识别、不做学习行为分析 |
| 提醒不打断思路 | 用**风扇物理风感 + 红色 LED**，而非响铃声 |
| 低成本可复制 | 2C4G 云服务器 + 现成预训练模型，月成本约 ¥60–100 |
| 隐私可控 | 照片上云即用即弃，云端**不落盘、不建库** |

### 1.2 明确不做的（阶段一）

- ❌ 玩手机检测、发呆走神、学习时长统计、每日报告 → 阶段二
- ❌ 多人识别、身份识别
- ❌ 模型微调（直接用 `yolov8n-pose.pt`）
- ❌ 数据库、MQTT、消息队列（HTTP 一问一答）
- ❌ 手机 App（安卓端为**草案**，见 `android/README.md`，尚未实现）

### 1.3 交付形态

```
┌────────────┐   10 秒/帧 JPEG   ┌──────────────────┐
│ ESP32-CAM  │ ───────────────▶ │ 云服务器 2C4G     │
│ + 风扇     │ ◀─────────────── │ FastAPI + OpenVINO│
│ + 红灯     │  {action: blow}  │ YOLOv8-pose       │
└────────────┘                  └──────────────────┘
```

## 2. 系统架构

### 2.1 物理组成

| 部件 | 型号 / 规格 | 作用 |
|---|---|---|
| 主控 + 摄像头 | AI Thinker ESP32-CAM（**必须带 PSRAM**，OV3660 或 OV2640） | 拍照、上传、驱动外设 |
| 风扇 | 5V 无刷涡轮鼓风机（≤0.3A，2 线） | 吹手提醒 |
| 开关管 | S8050（NPN，TO-92） | 用小电流 GPIO 控制风扇 |
| 续流二极管 | 1N5819 | 吸收电机断电尖峰 |
| 红灯 | 5mm 红色 LED + 220Ω | 视觉提醒 |
| 供电（调试） | USB-TTL 5V | 先跑通 |
| 供电（便携） | 18650（带保护板）+ TP4056 + XL3608-5V + 470~1000µF | 移动使用，续航约 8~11h |
| 服务器 | 阿里云 2 vCPU / 4 GiB / Ubuntu 24.04 | 推理与判定 |

### 2.2 软件组件

| 组件 | 技术栈 | 运行位置 | 职责 |
|---|---|---|---|
| 固件 | Arduino C++（ESP32 core 3.x） | ESP32-CAM | 定时拍照 → HTTP POST → 解析 `action` → 驱动风扇/LED |
| 云端服务 | Python 3.12 + FastAPI + uvicorn | 服务器 8000 端口 | 收图、鉴权、推理、规则判定、返回 JSON |
| 推理 | OpenVINO + YOLOv8n-pose | 服务器 CPU | 17 个关键点 |
| 多态检测（可选） | Qwen-VL + DeepSeek | 公网 API | 语义级行为判定，**默认关闭** |
| 标定工具 | Python 标准库 | 本地/服务器 | 手机拍照 → 实时看特征值 |
| 安卓端 | Kotlin（草案） | 手机 | 采集与观测，未实现 |

### 2.3 部署形态

```
公网 YOUR_SERVER_IP:8000
  ├── GET  /health   → {"status":"ok"}
  └── POST /detect   → 需要 X-Device-Key，body 为 JPEG
系统服务：posture.service（systemd，开机自启，--workers 1）
代码目录：/opt/posture（venv 在 /opt/posture/venv）
模型目录：/opt/posture/yolov8n-pose_openvino_model
配置来源：/opt/posture/.env（EnvironmentFile）
```

## 3. 关键设计决策

### 3.1 阶段一核心决策 D1–D13

| # | 决策项 | 结论 | 理由 |
|---|---|---|---|
| D1 | 监测对象 | 单人固定用户，无需身份识别 | 自己用 |
| D2 | 摄像头位置 | 桌上正对面平视，距头 0.5~0.6m | 能拍全上半身，关键点清晰 |
| D3 | 检测范围 | 仅坐姿端正（低头/驼背 + 侧歪） | 先做最简单可靠的 |
| D4 | 上传节奏 | 10 秒 1 帧 | 平衡实时性与流量/功耗 |
| D5 | 触发规则 | 连续 2 帧不端正 → 吹 5s；60s 内去重；恢复端正即停 | 防误报 + 防连环轰炸 |
| D6 | 灵敏度 | 先松后紧，标定后调整 | 初期宁可少吹 |
| D7 | 提醒方式 | 风扇吹 + 红色 LED（原设计含 BOOT 免打扰，**当前关闭**，见 §10.1） | 不吵、可物理感知 |
| D8 | 供电 | 18650(带保护板) + TP4056 + XL3608-5V | 便携可充电 |
| D9 | 光照 | 纯环境光；暗光"检测不到 → 不触发" | 宁漏报不误报 |
| D10 | 云端 | 2C4G 国内轻量 + CPU + OpenVINO + HTTP | 便宜、低延迟、无 GPU |
| D11 | 模型 | 现成 yolov8n-pose，不微调 | 先跑通 |
| D12 | 作息 | 无时段判断，开机工作关机结束 | 简单 |
| D13 | 开发环境 | 零 Arduino 经验 → 提供可直接编译的代码 | 降低门槛 |

### 3.2 安卓端决策 D14–D24（草案，未实现）

见 `android/README.md` §2。核心：原生 Kotlin APK、手动走系统相机 / 自动走 CameraX、
可配置服务器地址与密钥、10 秒/帧与固件对齐、CSV 导出标定记录。

### 3.3 实施中新增的工程决策（代码里有，文档里没有）

| # | 决策 | 原因 |
|---|---|---|
| E1 | 摄像头固定用 LEDC **channel 1**，风扇用 **channel 0** | ESP32 core 3.x 下 `ledcAttachChannel` 需显式分配，避免冲突 |
| E2 | OV3660 传感器启动时 `set_vflip(1)` | 该型号默认图像上下颠倒，不翻转会把"坐直"判成"驼背"，导致每 60s 误吹 |
| E3 | `camera_config_t config = {}` 零初始化 | 否则 `fb_location` 等字段是栈垃圾，初始化随机失败 |
| E4 | 免打扰按钮默认 **禁用** | GPIO0 与摄像头 XCLK（20MHz）冲突，当按键读会误触发 5 分钟免打扰（实测证实） |
| E5 | 风扇从 GPIO12 改 **GPIO13**，红灯改 **GPIO14** | GPIO12 与板载 microSD 共用 |
| E6 | WiFi 改 `WiFiMulti` 多网络 + `setSleep(false)` | 手机热点/家里 WiFi 自动切换，且降低断线概率 |
| E7 | 用 `JsonDocument`（ArduinoJson v7 动态分配） | 线上响应含 `state`/`source`，固定 256 字节缓冲有溢出风险 |
| E8 | 服务端显式 `float()` 转换 | numpy float32 不能直接 JSON 序列化，否则 `/detect` 必 500 |
| E9 | systemd 加 `EnvironmentFile` + `User=root` | 原版 `.env` 不生效、且要求不存在的 `posture` 用户 |
| E10 | `--workers 1` | "连续 2 帧"计数在进程内存，多进程会各算各的 |

## 5. 端到端数据流

### 5.1 正常一帧（端正）

```
[ESP32] 每 10s 触发
  拍照 VGA(640×480) JPEG ← PSRAM 双缓冲
  POST /detect  (X-Device-Key, image/jpeg)
        │
        ▼
[云端] 校验 key → letterbox 到 640×640 → OpenVINO 推理 (1,56,8400)
  argmax(score) ≥ 0.5 ? 取 17×3 关键点
  unletterbox 还原坐标 → 除以肩宽归一化
  头高 = (左肩Y+右肩Y)/2 − 鼻Y，再 / 肩宽
  肩平差 = |左肩Y − 右肩Y|，再 / 肩宽
  头高 ≥ 0.37 且 肩平差 ≤ 0.03 → 端正
        │
        ▼
[规则引擎] 端正 → bad_streak 归零 → action=none
        │
        ▼
[ESP32] 解析 action → none → 什么都不做
```

### 5.2 触发一次提醒（不端正）

```
0s  第 1 帧：不端正 → bad_streak=1 → none
10s 第 2 帧：不端正 → bad_streak=2 ≥ 2
      且距上次吹风 > 60s → action=blow, bad_streak 归零
[ESP32] 收到 blow → STATE_BLOWING：风扇 255/255，红灯亮
5s  定时到 → STATE_NORMAL：风扇 0，红灯灭
70s 若仍不端正且已过 60s → 再次 blow
```

### 5.3 无法判定（无人/太暗/关键点置信度低）

```
关键点 conf < 0.5 或 shoulder_width ≈ 0
  → features.valid=False → is_upright() 返回 None
  → 规则引擎把 None 当作"重置连续计数"，返回 none
  → 不触发（宁漏报不误报）
```

### 5.4 多态检测（可选，默认关闭）

```
每帧都尝试 run_async()，但 should_run() 限制为每 30s 一次且需两个 key 齐备
       │
       ├─ AI-1 Qwen-VL：JPEG → {person_present, scene, posture_hint, object_hint}
       └─ AI-2 DeepSeek：视觉描述 + 最近 5 条状态 → {state, upright, should_alert, confidence, reason}
       ▼
融合到下一帧的 fuse()（异步，结果滞后一帧）
```

> ⚠️ 慢速结果**异步**：本帧触发的检测，结果要到后续请求才被融合读取。

## 6. 接口契约

### 6.1 `GET /health`

| 项 | 值 |
|---|---|
| 鉴权 | 无 |
| 响应 | `{"status":"ok"}` |
| 用途 | 存活探针、部署自检 |

### 6.2 `POST /detect`

**请求**

| 项 | 值 |
|---|---|
| Header | `X-Device-Key: <DEVICE_KEY>`（必须） |
| Header | `Content-Type: image/jpeg` |
| Body | JPEG 原始二进制（**不是 multipart**） |

**响应字段（当前代码）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `action` | `"blow"` \| `"none"` | 固件只认这个字段 |
| `upright` | `true` \| `false` \| `null` | null = 无法判定 |
| `state` | string | `upright` / `slouch` / `unknown` / 慢速通道状态 |
| `source` | string | `fast` / `slow` / `fused` |
| `head_height` | float | 仅快速通道命中时返回 |
| `shoulder_level` | float | 同上 |
| `reason` | string | 判定原因 |

**错误码**

| 码 | 触发条件 | 响应体 |
|---|---|---|
| 401 | `X-Device-Key` 不匹配 | `{"detail":"invalid device key"}` |
| 400 | body 为空 | `{"detail":"empty body"}` |
| 500 | JPEG 解码失败 / 推理异常 | `{"detail":"<异常信息>"}` |
| 405 | 用 GET 请求 `/detect` | —（仅允许 POST） |

### 6.3 响应样例（2026-10-08 线上实测）

```json
// 端正
{"action":"none","upright":true,"state":"upright","source":"fast","head_height":0.672,"shoulder_level":0.025,"reason":"fast_path_ok"}

// 不端正（第 1 帧，未触发）
{"action":"none","upright":false,"state":"slouch","source":"fast","head_height":0.384,"shoulder_level":0.334,"reason":"fast_path_bad"}

// 不端正（第 2 帧，触发吹风）
{"action":"blow","upright":false,"state":"slouch","source":"fast","head_height":0.528,"shoulder_level":0.286,"reason":"fast_path_bad"}

// 无人 / 无法判定
{"action":"none","upright":null,"state":"unknown","source":"fused","reason":"cannot_determine"}
```

## 9. 版本基线与线上一致性

| 项 | 说明 |
|---|---|
| 权威版本 | `学习状态监测系统/`（B 版，含多态检测） |
| 旧版本 | `历史/旧版副本-项目内学习状态监测系统/`（A 版，无多态检测，**不要修改**） |
| 线上服务 | 与权威 `cloud/` 代码**逐字节一致**（`运维手册.md` §5，md5 全对） |
| 唯一已知差异 | 服务器 `/opt/posture/requirements.txt` 是未钉版本的旧文件；重建环境时须用本地权威版 |
| `.env` | 线上与灾备 `服务器备份/cloud_env/.env` 一致 |

**结论**：本地权威代码 = 线上运行代码。修改 `cloud/` 后必须重新部署才会生效。

## 10. 风险与已知限制

### 10.1 功能性限制

| 限制 | 影响 | 现状 |
|---|---|---|
| **免打扰按钮已禁用** | 无法临时手动静音 | `BUTTON_ENABLED=0`。原设计 GPIO0 与摄像头 XCLK 冲突，实测误触发。需外接按键到空闲脚（如 GPIO15）并改两行宏 |
| **侧歪检测不可靠** | 侧歪可能漏报或误报 | 9-25 标定样本区分度极小（0.0050 vs 0.0065）；10-08 实测 shoulder_level 达 0.286~0.334，说明阈值 0.03 对侧歪很敏感，需按新样本重标 |
| 暗光失效 | 晚上不吹 | 已接受（D9） |
| WiFi 抖动 | 偶发丢帧 | 已接受，固件自动重连 |
| 单帧视角依赖 | 摄像头位置变了就要重标 | 需固定机位（D2） |

### 10.2 运维风险

| 风险 | 说明 |
|---|---|
| 🔴 服务器 2026-10-25 到期 | 距今 **7 天**。到期不续费 → IP 变 → 固件必须重烧、模型重导 |
| 🔴 root 密码登录开启 | 存在爆破风险，建议 `PermitRootLogin prohibit-password` |
| 🟡 `DEVICE_KEY` 曾出现在对话记录 | 介意可 `openssl rand -hex 16` 轮换，同步改 `.env` 与 `config.h` |
| 🟡 `config.h` 明文存 WiFi 密码 | 分享工作区前需脱敏 |
| 🟡 服务内存约 415 MB | 4 GiB 规格内，可接受 |

## 11. 路线图

### 阶段二（代码已预留接口）

- **玩手机 / 发呆**：`multimodal.py` 已定义 `phone` / `daze` / `away` / `sleep` 状态，开启慢速通道即可接入
- **学习数据统计**：需新增时序存储（当前刻意无数据库）
- **模型微调**：AutoDL 租卡，冻结 backbone，50 epoch

### 安卓端（草案）

见 `android/README.md`：A1 骨架 → A2 设置页 → A3 自动模式 → A4 CSV 导出 → A5 本地提醒 → A6 联调。

### 工程改进建议

1. 外接免打扰按键（GPIO15），恢复 D7
2. 重新采集侧歪样本，重标 `SHOULDER_LEVEL_MAX`
3. 服务器续费或迁移到新 IP，同步固件
4. 轮换 `DEVICE_KEY`
5. 安卓端落地后，与 ESP32 分 key 计数，避免互相干扰
