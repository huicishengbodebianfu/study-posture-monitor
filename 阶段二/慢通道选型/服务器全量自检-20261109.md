## 二、慢通道:脚本口径偏乐观,实际更好也更险

脚本报 `4/4(≥80%)` 和 `6.67s`,但抓 journal 原始日志后,真实情况是:

```
slow-path ok  tries=3  latency=12.31s
slow-path ok  tries=3  latency=10.29s
slow-path ok  tries=3  latency=6.00s
slow-path ok  tries=2  latency=4.95s
slow-path ok  tries=2  latency=5.43s
pool failed : 0 次
```

**三个必须知道的差异:**

1. **真实成功率是 5/5,不是 4/4。**
   脚本有 1 轮记为"窗口内未完成"(SKIP/None),但日志显示那一轮最终也
   `slow-path ok`,全程 `pool failed` 为 0。也就是说 **没有真实失败**,是脚本没等到。

2. **12.31s 那条被脚本漏采了,平均延迟因此被低估。**
   脚本 4 个样本 26.67s → 6.67s;把漏掉的 12.31s 计入后是 38.98s/5 → **7.80s**。
   结论仍然是"达标(<8s)",但余量只剩 0.2s,不是报告里的 1.3s。

3. **有 2 次慢通道是被 [D] 的 120 帧突发流量带出来的**(20:38:55 那次),
   不完全由 `[F]` 的 5 轮显式触发。这也解释了为什么 `[F]` 第 1 轮的窗口里
   已经"没有新日志可等"——上一发还在 TTL/去重窗口内。

### 成因:20s 观测窗对 15s deadline 太紧

`check_slow()` 的做法是 `post → sleep(20) → journalctl --since t0`。
而慢通道预算 `AI_PARALLEL_DEADLINE=15s`,本轮实测出现 `tries=3`(重试两次),
一次 10~12s 的调用加上入队/重试开销,很容易把"成功"落在 20s 窗口之外。

**建议改法**(二选一,都不影响现有判定语义):
- `sleep(20)` → `sleep(30)`,单轮最坏 ~35s,5 轮仍在 3 分钟量级;
- 或改为"先跑完全部 rounds,最后统一按 `--since 起始时间` 抓一次日志统计",
  彻底消除逐轮竞态,顺带拿到全部样本算平均延迟。

## 三、值得留意但不是问题的三点

1. **`tries=3` 出现 2 次**:上游偶发空响应触发了池内重试,最终都成功。
   这是设计好的韧性行为(`AI_QUORUM=2` 投票后仍有兜底),不算故障。
2. **12.31s 已逼近 15s deadline**:如果再叠加一次重试就会超时。
   慢通道延迟分布是"两峰"——要么 5s 级,要么 10~12s 级,后者频次值得盯。
3. **配额台账**:自检时 `openrouter.ai` 已用 3/50,本次全量又消耗 5 次真实模型
   调用(其余后端走 sensenova 等)。日常自检用 `--no-slow` 可以不花钱。
