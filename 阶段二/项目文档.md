## 4. H1 · 硬件平台升级

### 4.1 为什么要换

阶段一的硬件瓶颈是**引脚冲突与资源不足**，直接导致 3 个功能无法实现：

| 阶段一问题 | 根因 | ESP32-S3 的解法 |
|---|---|---|
| 免打扰按钮不可用 | GPIO0 同时是摄像头 XCLK（20MHz 时钟输出） | S3 的摄像头引脚与启动引脚分离，GPIO0 可安全用作输入 |
| 风扇/LED 引脚紧张 | GPIO12 与 microSD 共用，被迫改到 13/14 | S3 可用 GPIO 更多（≥ 20 个），可重新规划 |
| 烧录必须 USB-TTL | ESP32-CAM 无原生 USB | S3 支持 USB OTG / USB-Serial-JTAG，可直接用 USB 线烧录与调试 |
| 无算力余量跑自检 | 单核 240MHz，PSRAM 仅够用 | S3 双核 + 512KB SRAM + 集成 PSRAM 选项 + ESP-NN 指令加速 |

### 4.2 选型要求（最低）

- **主控**：ESP32-S3（推荐 ESP32-S3-WROOM-1 或市售 ESP32-S3-CAM 模组）
- **摄像头**：OV2640 / OV3660 均可，确认与 S3 的 `esp32-camera` 引脚定义匹配
- **PSRAM**：必须 ≥ 4MB（一张 JPEG 帧缓冲需要）
- **USB**：优先选带 USB OTG 接口的开发板（免去 USB-TTL 下载器）

### 4.3 独立扩展板

把"主控"与"外设"物理分离：

```
┌─────────────────────┐      排线（电源+信号）      ┌───────────────────┐
│  ESP32-S3-CAM 板    │ ◀────────────────────────▶ │  独立扩展板        │
│  - 摄像头            │                            │  - 风扇驱动(S8050) │
│  - WiFi/BT           │                            │  - 红灯/状态灯     │
│  - USB 烧录口        │                            │  - 安静开关        │
│                     │                            │  - 电源总开关      │
│                     │                            │  - 5V 母线 + 电容  │
└─────────────────────┘                            └───────────────────┘
```

**好处**：
- 主控坏了只换主控，外设接线不动；
- 结构上摄像头可以固定在支架上，不再受杜邦线拉扯；
- 扩展板可以单独做 PCB 或洞洞板，与主控迭代解耦。

### 4.4 对固件的影响（需改，不改则无法运行）

1. **摄像头引脚重定义**：S3 的摄像头引脚与 ESP32-CAM 不通用，`main.ino` 顶部的 `#define PWD_GPIO_NUM` 等 14 个引脚必须按 S3 的参考设计重配。
2. **`ledcAttachChannel` 兼容性**：ESP32 core 3.x 下 `ledcSetup/ledcAttachPin` 已移除，阶段一已改用 `ledcAttachChannel`；S3 的 LEDC 通道数更多，需确认 channel 0/1 分配不变。
3. **恢复按钮逻辑**：`config.h` 的 `BUTTON_ENABLED` 从 `0` 改回 `1`，`PIN_BUTTON` 改到 S3 的空闲 GPIO（建议 GPIO16 或类似非 strapping 脚）。
4. **烧录方式**：若板载 USB，则不再需要"GPIO0 接 GND 再按 RST"的步骤；若仍用 USB-TTL，步骤不变。
5. **WiFi 与 HTTP 逻辑不变**：`uploadAndHandle()`、`connectWiFi()` 无需改动。

### 4.5 风险

- ⚠️ `esp32-camera` 对 S3 的支持晚于 ESP32-CAM，需确认所选板卡的引脚定义在社区已有成熟示例（推荐直接用市售 ESP32-S3-CAM 开发板的官方引脚表）。
- ⚠️ S3 的 USB OTG 烧录在部分 Windows 系统上需要额外驱动（ESP32-S3 USB-Serial-JTAG），提前准备。

### 5.3 服务器寻址：直接使用 IP（放弃域名方案）

**决策**：阶段二**不购买域名**，固件与客户端均直接使用服务器公网 IP。

```
固件:  SERVER_URL  "http://YOUR_SERVER_IP:8000/detect"
```

**为什么放弃**：
1. **备案问题**：新服务器在成都（国内地域），域名指向国内服务器按法规需要 ICP 备案，周期 2~20 天，且需要主体资质，对一个学生项目得不偿失。
2. **收益有限**：阶段二只有一台服务器，换服务器时重烧一次固件即可（阶段二本就有 H1 新平台烧录、H3 开关改动等需要重烧的动作，多一次不亏）。
3. **DNS 解析反而引入风险**：ESP32 的 `WiFi.hostByName` 依赖路由器 DNS；若 DNS 不可达，整个设备瘫痪且难以排查。用 IP 反而更确定。

**换服务器时的代价与对策**：

| 代价 | 对策 |
|---|---|
| IP 变了要重烧固件 | 阶段二烧录包已做成"双击 flash.bat"，重烧成本约 1 分钟；且 H1 换 S3 本来就要烧一次 |
| 安卓端要改配置 | 安卓端设置页本就支持改服务器地址（§9.3），无需改代码重打包 |
| 人工记 IP | 写在 `阶段二/服务器记录.md` 里，与 `服务器/` 目录统一管理 |

**保留的灵活性**：安卓端与 `tools/capture_server.py` 的服务器地址都是**可配置的**，只有固件硬编码 IP。若日后确实需要域名解耦，只需改固件一处，其余不变。

## 6. H3 · 人机交互恢复

### 6.1 安静开关（免打扰）—— 恢复

阶段一的免打扰因 GPIO0 与摄像头 XCLK 冲突而被禁用（`BUTTON_ENABLED=0`）。H1 换 S3 后引脚不再冲突，**恢复此功能**。

**设计要求**：
- 使用**物理拨动开关**（而非按钮），拨到"安静"位即进入免打扰，拨回即恢复——比"按一下"更符合直觉，也不存在误触退出的问题。
- 接 S3 的空闲 GPIO（内部上拉），开关另一端接 GND。
- 免打扰时：**红灯常亮、风扇不转、不上传**（与阶段一 `STATE_SNOOZE` 语义一致）。
- 固件逻辑不变（`enterSnooze()` / `enterNormal()`），仅恢复使能。

**配置变更**：
```c
#define BUTTON_ENABLED 1
#define PIN_BUTTON      <S3 空闲 GPIO，待分配>
```

### 6.2 电源总开关

阶段一设计了拨动开关串在电池正极主回路（`接线图.md` §5.2），但实际未安装。阶段二**必须安装**：

- 选型：船型开关（带 ON/OFF 标识）或带锁定的拨动开关，额定 ≥ 2A。
- 位置：装在扩展板外壳上，靠近电池入口。
- 作用：彻底断电，避免电池长期小电流自放电（TP4056 待机也有几 mA）。

### 6.3 状态指示灯（增强）

阶段一只有 1 个红灯，且"红灯亮 + 风扇停"在阶段一被标注为"不会出现"（旧的免打扰状态）。阶段二用这颗灯表达更丰富的状态：

| 灯状态 | 含义 | 固件状态 |
|---|---|---|
| 灭 | 关机 / 未通电 | — |
| **绿常亮** | 正常运行中 | `NORMAL`，`cam_ok=true`，WiFi 连通 |
| **绿闪烁**（1Hz） | 正常运行，刚上传完一帧 | `NORMAL`，上传周期内 |
| **红常亮** | 免打扰（安静开关打开） | `SNOOZE` |
| **红闪烁** | 正在提醒（吹风 5s） | `BLOWING` |
| **黄常亮** | 降级运行：摄像头不可用或 WiFi 断连 | `NORMAL` 但 `cam_ok=false` |
| **黄闪烁** | 自检失败 / 连续 N 次上传失败 | 需新增状态 |
| **黄红交替** | 严重故障（需人工干预） | 固件 bug 或硬件故障 |

> **实现建议**：若只有一颗红灯，可用闪烁模式区分；若扩展板上加一颗双色 LED（共阴红绿），可实现黄 = 红 + 绿同时亮。**【TBD】** 选用单灯闪烁方案还是双色灯方案。

## 7. H4 · 设备自检与状态增强

### 7.1 开机自检程序（Power-On Self Test, POST）

上电后、进入 `NORMAL` 状态前，按顺序执行：

```
1. 摄像头初始化 → 抓一帧验证（复用 initCameraOnce() 的 probe 逻辑）
2. WiFi 连接 → 至少一个 known network 连通
3. 云端握手 → GET /health 返回 {"status":"ok"}
4. 密钥校验 → POST 一张空/小图，确认不返回 401（验证 DEVICE_KEY 一致）
5. 外设通路 → 风扇 PWM 输出一个极短脉冲（≤200ms）+ LED 亮灭一次，验证驱动管正常
6. 阈值确认 → 若云端返回的阈值与固件期望差异过大，记录告警
```

**任一失败不阻塞运行**：摄像头失败 → 进入降级模式（§7.2）；WiFi 失败 → 持续重试；云端失败 → 静默跳过。

**自检结果暴露**：`GET /status` 增加字段：
```json
{
  "cam_ok": true,
  "wifi": true,
  "ip": "192.168.1.100",
  "state": 0,
  "uptime_s": 1234,
  "selftest": {            // 新增
    "passed": true,
    "failed_items": ["fan"], // 失败项列表
    "detail": "fan pulse not detected"
  },
  "server_reachable": true,
  "key_ok": true
}
```

### 7.2 降级模式（Graceful Degradation）

阶段一已实现"摄像头失败时不重启、每 30s 重试、`/status` 可查看"。阶段二**扩展降级维度**：

| 故障 | 降级行为 |
|---|---|
| 摄像头不可用 | 不上传；红灯黄灯指示；定时重试；`/status` 报 `cam_ok=false` |
| WiFi 断连 | 停止上传；本地计数保持；重连后继续 |
| 云端返回 500/超时 | 本帧按"无法判定"处理，不触发提醒；连续 3 次失败 → 黄灯闪烁告警 |
| 密钥不一致 | 立即黄灯闪烁 + 日志告警（避免静默失败） |
| 风扇驱动异常 | 红灯正常亮但风扇不转 → 属于硬件故障，黄红交替闪烁 |

### 7.3 备用 ESP32-S3（"性能不足时的第二块板"）

用户提出"如果性能不足还有单独的一块 ESP32-S 可使用"。经评估：

**ESP32-S3 双核 240MHz 运行本项目的负载极低**（阶段一实测服务器 0.1fps、CPU 1%；ESP32 侧仅做 HTTP 一问一答），**不存在性能不足需要第二块板的情况**。

因此第二块 ESP32-S3 的合理定位不是"算力补充"，而是：

| 用途 | 说明 |
|---|---|
| **看门狗 / 独立状态指示** | 第二块板通过一根 GPIO 读取主控的"心跳"脉冲；主控卡死时，第二块板控制红灯闪烁告警，甚至硬件级切断风扇电源 |
| **传感器协处理器** | 若阶段二加入环境光传感器、温湿度、人体红外等，由第二块板采集并通过 UART 上报 |
| **备用整机** | 作为"换板即用"的备件，而非同时运行 |

**建议**：阶段二先不做第二块板，把 H1~H5 跑通；若确有看门狗需求，在 M6 之后作为 **H4.2** 追加。**【TBD】** 是否采购第二块 ESP32-S3。

### 8.1 现状

> **阶段二实测（2026-11-01）：慢通道已在生产环境跑着，不是"未实测"。**

服务器当前配置（来自 `/opt/posture/.env` 实测）：

| 项 | 值 |
|---|---|

| `MULTIMODAL_INTERVAL` | `30`（秒） |
| `MULTIMODAL_TTL` | `90`（缓存有效期，≥ 3 倍 interval） |
| `MULTIMODAL_MIN_CONF` | `0.6`（翻案最低置信度） |
| 模型 | **`sensenova-6.8-flash-lite`**（单次调用方案） |
| 网关 | `https://token.sensenova.cn/v1` |
| `AI_SINGLE_CALL` | **`true`**（AI-1+AI-2 合一，一次请求直出） |
| 两段式备用 | `DEEPSEEK_API_KEY` 已设但不用（`AI_SINGLE_CALL=true`） |

**已拉取的服务器代码（`阶段二/server-sync/`）揭示的实现细节**：

- `multimodal.py`：`single_call=True` 时，一次 Qwen 请求直出 `state/upright/confidence/should_alert`，经 `schema.should_alert()` 门控后写入缓存；`_run` 有 `max_tries=2` 重试，失败不写缓存（让旧结果自然过期）。
- `schema.py`：**新增的契约模块**——`VALID_STATES` 枚举、`_STATE_ALIASES` 别名表（`head_down→slouch`、`writing→upright` 等）、`_FIELD_ALIASES` 字段别名、`normalize()` 强校验（任何异常输入返回合法 dict，绝不抛异常）、`should_alert()` 唯一翻案判定点。
- `ai_providers.py`：`VisualDescription` 新增判定字段（`state`/`upright`/`confidence`/`should_alert`/`needs_review`），`_parse` 统一走 `schema.normalize`。
- `app.py`：`/detect` 走 `fast → multimodal.run_async → fuse → rule_engine.update` 流水线。

**实测日志（证明慢通道在跑）**：见 §5.1。

### 8.2 当前方案与阶段一设计的差异

| 维度 | 阶段一设计文档 | 服务器实际（阶段二） |
|---|---|---|
| 调用方式 | 两段式：AI-1 看图 → AI-2 决策 | **单次调用**：一次请求直出判定（`AI_SINGLE_CALL=true`） |
| 模型 | Qwen-VL + DeepSeek | **sensenova-6.8-flash-lite** |
| 融合门控 | 任意通道不端正 → blow | 慢通道翻案必须 `should_alert=True` **且** `confidence >= 0.6` |
| 状态集 | `upright/slouch/lean/phone/daze/away/sleep/unknown` | 一致，但增加了 `ALERTABLE_STATES = {slouch, lean, phone, daze}`（`sleep/away` 只记录不提醒） |
| 重试 | 无 | `max_tries=2`，失败不写缓存 |
| 缓存 TTL | 无 | `result_ttl=90s`，过期回退快速通道 |

> **为什么这个差异重要**：阶段一文档 §8.3 的"两段式"选型表（A/B/C）已经**被服务器实际部署覆盖**。阶段二若要改模型，只需改 `.env` 里的 `AI_BASE_URL` / `AI_MODEL` / `AI_API_KEY` 三行，`ai_providers.py` 和 `multimodal.py` 无需改动（`QwenVLProvider.analyze()` 本就是通用的 OpenAI 兼容接口）。

### 8.3 慢通道开启步骤（已开启，供回滚/迁移参考）

```bash
# 1. 编辑 /opt/posture/.env
MULTIMODAL_ENABLED=true
MULTIMODAL_INTERVAL=30
MULTIMODAL_TTL=90
MULTIMODAL_MIN_CONF=0.6
AI_SINGLE_CALL=true
AI_BASE_URL=https://token.sensenova.cn/v1
AI_API_KEY=<redacted>
AI_MODEL=sensenova-6.8-flash-lite

# 2. 重启服务
sudo systemctl restart posture

# 3. 验证（慢通道每 30s 才跑一次，需等一个周期）
sudo journalctl -u posture -f | grep multimodal
# 预期输出：multimodal: state=phone upright=False alert=True conf=0.98 ...
```

**回滚**：把 `MULTIMODAL_ENABLED` 改成 `false` 并重启，系统完全等同于阶段一。

### 8.4 融合策略（当前服务器实际行为）

| 快速通道 | 慢速通道 | 融合结果 |
|---|---|---|
| 明确不端正 | — | **不端正**（快速通道优先，`source=fast`） |
| 无法判定 | 慢通道不端正 **且** `should_alert=True` **且** `conf >= 0.6` | **不端正**（慢通道翻案，`source=slow`） |
| 无法判定 | 慢通道不端正但 `should_alert=False`（如"正常低头看书"） | 无法判定（`slow_no_alert:xxx`，不触发） |
| 明确端正 | — | 端正（`source=fast`） |
| 无法判定 | 慢通道端正 | 端正（`source=slow`） |
| 无法判定 | 无慢通道结果 | 无法判定（`source=fused`，不触发） |

> 关键改动：**慢通道翻案必须同时满足 `should_alert=True`**。模型判了 `slouch` 但明确 `should_alert=false` 时不再翻案，避免把"低头看书"当成驼背吹风。

### 8.4 慢通道引入的新问题（阶段二必须解决）

1. **成本**：默认 30s 一次，4h 学习时段约 480 次调用。需实测单次费用，若过高则调大到 60s。
2. **延迟**：慢通道在后台线程，**不阻塞主请求**——HTTP 一问一答的响应时间不受影响。但慢通道结果有缓存有效期（`TTL=90s`），过期后回退快速通道。
3. **状态集扩展**：慢通道可返回 `phone / daze / away / sleep`。**服务器已通过 `ALERTABLE_STATES = {slouch, lean, phone, daze}` 解决**（`sleep`/`away`/`upright`/`unknown` 不可提醒）。阶段二要确认的是：`phone` 和 `daze` 是否真的需要触发吹风——当前代码允许，但实际策略待业务确认。
4. **与计数器的干扰**：慢通道异步结果写 `_last_result`，主线程读——当前实现有 `_lock` 保护，线程安全。但**手机/浏览器手动调用 `/detect` 仍会干扰"连续 2 帧"计数器**（阶段一已知问题，阶段二需落地 `?source=mobile` 隔离）。
5. **负 head_height 问题**：实测日志出现 `head_height=-0.357` 和 `-0.626`（鼻子在肩膀下方），说明真实摄像头角度与标定假设不一致。这是**现场重标定**的需求，不是代码 bug——阶段二需要用新服务器 + 真实坐姿重新跑 `calibrate.py`。

## 10. H5 · 硬件优化

### 10.1 供电（阶段一问题 #4：掉线不稳）

阶段一现象：2026-10-08 多次整段失联，随后自行恢复。可能原因：电池低压保护、风扇启动电流拉垮 5V、XL3608 低输入电压下带不动瞬时负载、接线接触不良。

**阶段二措施**：

| 项 | 做法 | 验收 |
|---|---|---|
| 升压芯片评估 | XL3608 实测在电池电压 <3.5V 时输出不稳 → 评估替换为同步升压芯片（如 FP6291、MT3608 改进版）或 5V 固定输出模块 | 电池从 4.2V 放到 3.3V 全程 5V 输出不跌落 |
| 5V 母线电容 | 确认已并联 470~1000µF 电解电容，且尽量靠近 ESP32-CAM 的 5V 引脚 | 风扇启动瞬间 5V 不低于 4.5V（万用表/示波器实测） |
| 电池电量监测 | 用 S3 的 ADC 读电池分压，低电量时黄灯闪烁 + `/status` 报 `battery_low` | 3.3V 以下告警 |
| 接线 | 杜邦线改为焊接或 PH2.0 端子，关键连接点加热缩管 | 晃动测试不断连 |

### 10.2 风扇与风道

- 风扇出风口加**导风嘴**或短软管，确保风吹到手背（阶段一实测送风距离不足）。
- 风扇堵转检测：若 PWM 输出但电流异常（可用串联小电阻 + ADC 采样，或简单地在固件里记录"吹风扇时是否被手动按住"），黄灯告警。
- 风扇噪声：若仍吵，换 5V 无刷涡轮（双滚珠），接线不变。

### 10.3 结构与摄像头固定

**这是阶段二最容易被忽视但影响最大的一项**：阈值 `0.37/0.03` 是在特定摄像头位置下标定的。摄像头一旦被移动（杜邦线拉扯、手碰），阈值立刻失效，导致误报或漏报。

- 3D 打印（或硬纸板 + 胶带）做一个**摄像头支架**，把摄像头固定在桌面上方 0.5~0.6m、正对人脸的位置。
- 排线用扎带固定，避免拉扯。
- 支架上预留安静开关、电源总开关、状态灯的位置。

### 10.4 补光（可选）

阶段一接受"暗光不检测"（D9）。阶段二若希望晚上也能用：
- 加一颗 USB 供电的**暖光小台灯**（不可用红外，OV2640/OV3660 对红外敏感会偏色）。
- 补光灯由 S3 的一个 GPIO 经 MOS 管控制，仅在环境光低于阈值时打开。
- **【TBD】** 是否加入补光（涉及物料与结构变更）。

### 11.2 端到端数据流（一次提醒）

```
0s   ESP32 拍照 → POST /detect → 快速通道判定"不端正"（第1帧）→ 返回 none
     └─ 同时触发慢通道（若开启，异步，不阻塞响应）

10s  ESP32 拍照 → POST /detect → 快速通道判定"不端正"（第2帧）
     └─ 连续 2 帧达成 → 返回 blow
     └─ ESP32 进入 BLOWING → 风扇 5s + 红灯闪烁

15s  5s 定时到 → NORMAL → 风扇停、红灯灭

70s  若仍不端正且距上次吹已 60s → 再次 blow

慢通道（每 30s）：JPEG → Qwen-VL 视觉描述 → DeepSeek 行为判定 → 缓存结果
     若慢通道判定"不端正"而快速通道"无法判定" → 融合层翻案 → blow
```

## 13. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| ESP32-S3 摄像头引脚无成熟示例 | M7 阻塞 | 选型时确认板卡官方提供 CameraWebServer 示例；备选换回 ESP32-CAM + 外接按钮到 GPIO15 |
| 新服务器到期后 IP 再变 | 固件需重烧 | 双击烧录包约 1 分钟；阶段二本就要重烧，代价可控 |
| 慢通道 API 费用超预期 | 持续成本 | 先设 `MULTIMODAL_INTERVAL=60`，实测 1 周后调；设月度预算告警 |
| 安卓端后台定时被系统杀 | 自动模式不可用 | 降为手动 + 前台服务通知；不强求严格 10 秒 |
| 摄像头支架设计迭代慢 | M13 延期 | 先用纸板/胶带固定验证位置，再 3D 打印 |
| 第二块 ESP32-S3 定位不清 | 范围蔓延 | 阶段二先不做，M6 后评估（§7.3） |
| 旧服务器到期后数据丢失 | 阻断 | 已解决：新服务器已上线，本地备份 5/5 MD5 通过 |

## 14. 与阶段一的兼容性

### 14.1 必须保留（不可退化）

- 快速通道逻辑（YOLOv8-pose → 头高/肩平差 → 连续 2 帧 → 60s 去重）
- `POST /detect` 接口契约（`action` / `upright` / `head_height` / `shoulder_level` / `reason`）
- `GET /health` → `{"status":"ok"}`
- 照片不落盘、不建库、用完即弃
- `--workers 1`（多 worker 会破坏连续帧计数）
