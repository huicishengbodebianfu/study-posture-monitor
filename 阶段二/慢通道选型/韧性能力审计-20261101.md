## 二、逐项证据

### 1. 能力探测 —— 缺失

```python
# app.py:27
AI_BASE_URL = os.environ.get("AI_BASE_URL", "https://dashscope.aliyuncs.com/compatible-mode/v1")
# app.py:62
    base_url=AI_BASE_URL,
```

全仓没有任何 `/models` 调用（`probe`/`capability` 关键词命中 0）。
后果：把 `AI_MODEL` 写错一个字母、或换到一个不支持图片的模型，**服务照样启动成功、`/health` 照样 `ok`**，
直到第一次慢通道调用线上报错才发现。

### 2. 指数退避 —— 缺失

```python
# multimodal.py:169-176
for attempt in range(self.max_tries):      # max_tries=2，默认
    visual = self.qwen.analyze(image_bytes)
    if visual.ok:
        break
    last_err = visual.error
    log.warning("slow-path attempt %d/%d failed: %s", attempt + 1, self.max_tries, last_err)
```

两次调用之间**没有任何等待**（全仓 `time.sleep` 命中 0，之前的 21 次 `sleep` 命中全是状态名 `"sleep"`）。
遇到 429 时，第二次请求在几毫秒内立刻打出去，大概率再吃一次 429，等于把限流窗口钉死。

线上已经出现过这个代价：

```
11:13:06 [WARNING] slow-path model call failed: 'content'
11:13:06 [WARNING] slow-path attempt 1/2 failed: 'content'   ← 同一秒，背靠背
11:13:19 multimodal: state=daze ...
```

### 3. 超时降级 —— 具备，但有两个缺陷

链路是完整的：

```python
# ai_providers.py:192   timeout=self.timeout        (默认 20s)
# ai_providers.py:200   except Exception as e:      → VisualDescription(ok=False, error=...)
# multimodal.py:177     return  # 全部失败：不写缓存
# multimodal.py:256     if age > self.result_ttl: return None    (TTL=90s，过期即无结果)
# multimodal.fuse()     slow=None → 回退快速通道
```

设备侧不会被拖住：模型调用在后台线程，`/detect` 实测 0.09 s。

**缺陷 A：超时预算超过周期。** `20s × 2 次 = 40s`，而 `MULTIMODAL_INTERVAL=30`。
加上 `run_async` 的 `_running` 互斥（`multimodal.py:146`），一次超时会**吃掉两个抽查周期**，
且这期间日志里只有 WARNING，看不出"慢通道已停摆 60 秒"。

**缺陷 B：不区分失败原因。** 超时、鉴权错、格式错全部走同一个 `except Exception`，
日志只有 `str(e)`，无法按类型统计（这直接导致了 3.1 节那个 `'content'` 的 KeyError 只能靠人工猜）。

### 4. 429 自动切后端 —— 缺失

```python
# ai_providers.py:194
resp.raise_for_status()     # 429 → HTTPError → 通用 except → ok=False
```

没有 `status_code == 429` 分支，也没有第二个后端可切：

```
$ grep -c "FALLBACK\|BACKEND" /opt/posture/.env /opt/posture/app.py
/opt/posture/.env:0
/opt/posture/app.py:0
```

### 5. 故障切换 —— 缺失

单后端、无熔断。上游持续 5xx 时，每 30 s 一次、每次 2 连击，全部打空，
而且**没有任何"这台已经不行了，先别打"的记忆**（`circuit`/`breaker` 命中 0）。

### 6. 坏例落盘 —— 缺失

全仓 `json.dump` 只出现在 `posture.py` 的一条注释里；`open(` 只出现在 `calibrate.py` / `evaluate.py` 的读取路径。
慢通道失败时**只写 journald 一行**，没有：

- 原始图片（无法复现）
- 原始返回体（无法判断是限流、脏 JSON 还是空内容）
- HTTP 状态码 / 重试次数 / 后端名（无法统计）

## 三、补齐方案（已写好并单测通过，**尚未部署**）

新增一个不依赖 FastAPI 的独立模块，6 项一次补齐：

| 文件 | 作用 |
|---|---|
| `proposal/resilience.py` | `VisionPool`：能力探测 + 指数退避 + 超时 + 429 切后端 + 熔断 + 坏例落盘 |
| `tools/test_resilience.py` | 19 条断言，全部 mock，不发真实请求 |

### 3.1 模块能力对照

| 能力 | 实现位置 | 行为 |
|---|---|---|
| 能力探测 | `VisionPool.probe(deep=True)` | 先 `GET /models` 校验模型在目录里；再发 1×1 图验证真能收图。启动时打印能力表 |
| 指数退避 | `_backoff()` | `0.8s → 1.6s → 3.2s`，封顶 8 s，叠加 0~0.2 s 抖动 |
| 超时降级 | `analyze()` 的 `except requests.Timeout` | 按失败处理、**不写缓存**、换后端；整体失败返回 `ok=False`，上层自然回退快速通道 |
| 429 切后端 | `SWITCH_CODES = {429,500,502,503,504}` | 命中即 `breaker.fail(backend)` 并换下一台，**绝不原地重试** |
| 故障切换 | `CircuitBreaker` | 连续 3 次失败熔断 120 s；多后端轮转；全熔断时直接失败（`attempts=0`），不浪费调用 |
| 坏例落盘 | `BadcaseStore.save()` | `<dir>/YYYYMMDD/<ts>-<sha1>.json + .jpg`，含后端/模型/HTTP 码/返回体/原图；按天分目录、超 500 对自动删最旧 |

def analyze(self, image_bytes: bytes) -> VisualDescription:
    if not self.enabled:
        return VisualDescription(ok=False, error="api key not set")
    r = self.pool.analyze(image_bytes, PROMPT)
    if not r["ok"]:
        return VisualDescription(ok=False, error=f'{r["error"]} (tries={r["attempts"]})')

### 7.3 接线过程中实测抓出的 3 个问题

**① 原逻辑对 401 的处理是"整池放弃"（真 bug）**

首版把 `401/403` 当"永久错误"直接 `break`，导致主后端 Key 一旦失效，整个池子立刻放弃、备用后端根本轮不到。
改成：**永久错误只熔断该后端（`breaker.open_now`），继续试下一台**。单测已补对应用例。

```
slow-path permanent failure on broken-primary: HTTP 401 -> switching backend
{"ok": true, "backend": "fallback1", "model": "kimi-k2.6", "attempts": 2, "latency": 7.11}
```

**② 备用后端的超时不能和主后端共用**

`intern-s2` 从这台服务器实测 **38 s**（本地离线测是 11.4 s，跨境链路差很多），12 s 和 16 s 都必然超时。
于是给 `Backend` 加了 `timeout` 字段，允许按后端覆盖，并把预算断言改成"主 12 + 退避 0.8 + 备 16 = 28.8 ≤ 30"。

**③ 备用后端的选型被真实延迟推翻**

真实提示词（638 字符）下从服务器测得的候选：

| 模型 | 延迟 | 结果 |
|---|---|---|
| intern-s2 | 38.0 s | 不可用（超周期） |
| Sage-A1.5 | 11.1 s | HTTP 200 但**空 content**（推理吃光 800 token） |
| qwen3.8-27b | 9.9 s | 可用，但选型报告里端正误判 3/6 |
| **kimi-k2.6** | **8.1 s** | 可用，JSON 合法 |

最终选 **kimi-k2.6**。代价是 $24.9/千次，但只在主后端失败时才会打，按 1% 失败率估月成本 ≈ $3.6。

## 八、降低 VLM 推理强度以提速（2026-11-01 12:04 → 12:21 最终版）

目标：降低推理强度以提速，不是彻底下线。

| 外部 VLM（慢通道） | **已关闭**（`MULTIMODAL_ENABLED=false`） | 实测每次 8~12 s、每 30 s 触发一次，是唯一的重负载与网络抖动源 |

| 本地 YOLOv8-pose | **保留**（这是设备功能本体） | 单次 92 ms，每 10 s 一次 ≈ 0.9% CPU |

### 关闭效果实测

| 指标 | 关闭前 | 关闭后 |
|---|---|---|
| 出站模型连接 | 每 30 s 一次（8~12 s 占用） | **0**（`ss -tnp` 无对外连接） |
| `slow-path` / `multimodal` 日志 | 持续产生 | **0 条**（40 s 观察窗） |
| `/detect` 延迟 | 均值 91.8 ms | 均值 91.8 ms（快速通道未变） |
| 服务 CPU | 1.2% | 1.2% |

### 为什么没继续压 92 ms

| 尝试 | 结果 |
|---|---|
| `PERFORMANCE_HINT=LATENCY` + `INFERENCE_NUM_THREADS=2` | 91.0 → 88.7 ms（**2.5%**，可忽略） |
| 输入从 640 降到 480/416/320 | **不可行**：导出的 OpenVINO IR 把 8400 个 anchor 写死在后处理里，`reshape` 直接形状冲突；服务器上没有 `.pt`/`.onnx` 源权重可重导出 |
| 减少上传频率 | 属固件 `UPLOAD_INTERVAL_MS` 范畴，与加速目的相反（会更慢响应） |

**结论**：92 ms 不是瓶颈。设备 10 s 才上传一帧、HTTP 超时 8 s，92 ms 占其中 1%。真正的"推理强度"来自慢通道，已经关掉。

## 九、多备用 + 测速选路（2026-11-01 13:50）

需求：**不替换 kimi，而是再加一个备用**；备用之间**按实测速度挑最快的**。

### 9.1 后端配置

| 序号 | 名称 | 端点 / 模型 | 超时 | 角色 |
|---|---|---|---|---|
| 0 | primary | sensenova-6.8-flash-lite @ token.sensenova.cn | 12 s | 主用，永远优先 |
| 1 | fallback1 | kimi-k2.6 @ discovery-api | 16 s | 备用 |
| 2 | fallback2 | Sage-A1.5 @ discovery-api | 10 s | 备用 |

预算：`AI_MAX_TRIES=2`，每轮只挑一个备用 →
最坏耗时 = 12 + 0.8 + max(16,10) = **28.8 s ≤ 30 s**（启动断言会拦超预算配置）。

### 9.2 选路规则（`VisionPool._pick`）

```
主用可用            → 永远先用主用（不接受轮转，主备语义优先）
主用不可用/已试过    → 在备用里挑 EWMA 延迟最小的
从未测过速度的备用   → 排在最后但仍然可用（避免冷启动全挂）
```

延迟用指数滑动平均（α=0.3）随每次真实调用刷新，失败按"该后端超时值"计入惩罚。

### 9.3 启动测速

启动时后台线程对**每个备用**发一张 1×1 图测一次速度（不阻塞启动、不测主用）：

```
13:50:36 [WARNING] backup speed probe fallback1 failed: ReadTimeout (16.2s)
13:50:37 [INFO]    backup speed probe fallback2: ok 0.67s
```

→ kimi 记 16 s 惩罚，Sage 记 0.67 s，之后一旦需要备用，直接选 Sage。

### 9.4 验证

**A. 线上正常路径**（主用可用时不受影响）

```
slow-path ok backend=primary model=sensenova-6.8-flash-lite tries=1 latency=3.85s
```

**B. 主用失效时的实际选路**（用坏 key 模拟主用 401）

```
测速结果: fallback1 ewma=16 (失败1次) / fallback2 ewma=0.69
slow-path permanent failure on primary -> switching backend
→ backend=fallback2 model=Sage-A1.5 tries=2 latency=5.48s
```

即：三个后端并存 → 主用优先 → 主用挂了自动挑最快的备用，**跳过 16 秒的 kimi**。

### 9.5 目的与代价

- 目的：kimi 目前在 discovery-api 上已不可用（连纯文本都 60 s 超时），但保留它不影响选路——
  它只会因为 EWMA 最差而被排在最后，不会拖慢正常流程。
- 代价：每次重启多 2 次极小调用（1×1 图，8 token）；kimi 那次会在后台卡满 16 s，但**不阻塞启动**。

### 10.2 并发实现

`VisionPool` 新增并发模式：

```
AI_PARALLEL=true          开启多模型并发
AI_PARALLEL_MAX=2         每轮并发几个（0=全部）
AI_QUORUM=2               形成多数票所需票数
AI_PARALLEL_DEADLINE=15   整次分析的总截止（秒）
```

执行流程：

1. **主后端必选**（质量基线），剩余名额按 EWMA 实测速度补位；
2. 各后端**并发**发出（提交间隔 0.15 s，降低同网关瞬时 429）；
3. 等 `deadline` 秒，超时的直接放弃；
4. 对 `upright` **投票**：多数票胜出；票数不足 `quorum` 时退化为"置信度最高的单条"；
5. `state` 取胜出阵营里置信度最高的那个，`evidence` 写入各后端投票明细便于溯源。

### 10.3 修掉的两个并发 bug

**① deadline 形同虚设**：`with ThreadPoolExecutor(...)` 退出时会 join 所有线程，
实测 12 s 的 deadline 跑出了 16.2 s。改为手动 `shutdown(wait=False, cancel_futures=True)`。

**② 主后端被当成"未测速"一起排序**：并发选路时主用可能被排到慢号后面。
改为主用**无条件入选**，只用剩余名额挑最快的备用。

### 10.4 实测表现

| 轮次 | 结果 |
|---|---|
| 最好 | `backend=vote2/2 model=qwen3.8-27b,sensenova-6.8-flash-lite latency=5.5s` —— 两模型跨网关投票，5.5 秒出结果 |
| 常见 | `vote1/1` + 8~12 s —— 只有一台在 deadline 内返回，退化为单条 |
| 波动 | discovery-api 侧频繁 `ReadTimeout` / `empty content`，同一模型时会 0.6 s、时会 10 s+ |

**结论**：并发链路是通的、投票逻辑正确：**双票时 5.5 s 就能拿到跨网关一致结论**。
瓶颈不在我们的代码，而在 `discovery-api` 的稳定性——同一把 key 上并发 2~3 路会触发限流与超时。

### 10.5 调参与建议

| 现象 | 建议 |
|---|---|
| 双票率低 | 调大 `AI_PARALLEL_DEADLINE`（15→18，仍 < 30）、或把 `AI_PARALLEL_MAX` 降到 2 |
| 想省钱 | `AI_PARALLEL_MAX=1` 即退化为串行，成本回到原来水平 |
| 只要稳 | 把 `AI_PARALLEL=false`，走"主用 + 最快备用"的串行逻辑 |
| 成本提示 | 并发 N 台 = **N 倍调用量**。30 s 一帧、每天 4 h 学习，N=2 时约 960 次/天 |
