## 7.2 P0-3 帧指纹兼容(跨类型兜底)

**问题**:`frame_key` 在关键点有效时是几何元组 `(hh, sl)`、无效时是 `("img", phash)`,
**类型会在相邻帧之间翻转**;旧 `_same_scene` 遇类型不一致直接 `return False`,
导致"快通道一失效,慢通道的正确结论就永远匹配不上"。

**改法**
1. `MultimodalResult` 新增 `img_hash` 字段,慢通道每次落库时一并保存该帧的 256bit 感知哈希;
2. `run_async / _run / _run_single / _run_two_stage / fuse` 全链路透传 `img_hash`;
3. `_same_scene(cached_key, cur_key, cached_img, cur_img)` 重写:

   - 两边都是几何元组 → **保持原有 0.12/0.12 双阈值,不放松**

   - 缺几何指纹 → 也走图像指纹
4. `app.py`:`_phash = stats[3]`,同时传给 `run_async` 与 `fuse`;

## 7.3 P1-1 slow_override 护栏

**问题**:慢通道的否决权是**无条件**的 —— 只要它说"端正"且 `conf ≥ 0.9`,
就推翻快通道的"不端正"。而慢通道是 30s 一次的抽样,实测对同一坐姿给出
`away×6 / unknown×5 / upright×4 / slouch×3` 的互相矛盾结论。
一次误判"端正"就能让真正驼背的学生长时间收不到提醒。

**改法**
1. `MultimodalDetector` 新增 `_fast_bad_streak`:快通道连续判"不端正"的计数
   (判 `True` 归零,判 `None` 不打断也不累加);
2. 否决权新护栏:当 `_fast_bad_streak >= override_guard_frames`(默认 **3**)时,
   **禁止**慢通道翻案,并打一条 `slow_override blocked: ...` 日志;
3. 参数可配:`SLOW_OVERRIDE_GUARD_FRAMES`(0 = 关闭护栏,回到旧行为);
4. 启动日志已打印该值(见第一批改动 2)。

**为什么选 3 帧**:设备 10s 一帧,3 帧 = 30s 连续同向几何证据;
此时一个 30s 才抽样一次的 VLM 结论不足以整体否掉它。

**验证**

```

护栏=0 关闭          判好时 streak 归零
```

## 7.4 P2-1 后端选路:按**真实调用**耗时排序

**问题**:选路排序键一直是 `latency_ewma`(启动探测值)。探测发的是 1x1 小请求,
测到的主要是网络 RTT(实测 0.39~2.5s),而真实调用要跑视觉推理(实测 4~9s),
**两者排序经常相反** —— 这就是"主用明明更慢却总被优先选上"的根因。

**改法**
1. 新增 `VisionPool._speed_key(be)`:
   - `real_samples ≥ 2` → `(0, real_ewma)`(最可信)
   - 只有探测样本 → `(1, latency_ewma)`
   - 完全没测过 → `(2, inf)`(排最后但不排除)
2. `_pick`(串行)、`_analyze_parallel` 的 `rest.sort` / `fill.sort` 全部改用该键;
3. 配额可观测性:`_quota_ok` 命中"没额度"时,按账号 **10 分钟节流**打一条
   `quota exhausted: <account> (skipped until it resets)` —— 对应"偶尔没额度是正常的,
   但不能完全不可见"。

**验证**

```

OK 真实样本优先于探测样本 / 真实样本内部按 real_ewma 升序 /
   未测速排最后 / 探测样本排在真实样本之后 / 旧排序会排错、新排序纠正
```

## 8.1 为什么只修 `fuse` 不够

R3 其实有**两层**,只改一层是修不干净的:

| 层 | 位置 | 旧行为 |
|---|---|---|
| ① 采信 | `multimodal.py` `fuse()` 的 `trusted and slow.upright is True` 分支 | 没有任何置信度门槛,`conf=0.3` 的"端正"也返回 `upright=True` |
| ② 计数 | `posture.py` `RuleEngine.update()` 的 `upright is None` 分支 | **`None` 也把 `_bad_streak` 清零** |

如果只修 ①(改成返回 `None`),② 照样会把计数清零 —— 等于没修。
反过来只修 ②,`fuse` 仍会返回 `upright=True`,一样清零。

## 8.2 改法

### ① `multimodal.py`:低置信"端正"降级为"无法判定"

```python
if trusted and slow.upright is True:
    if slow.confidence < self.min_confidence:      # 默认 0.6
        return MultimodalResult(
            upright=None, state=slow.state, should_alert=False,
            source="slow",
            reason=f"slow_low_conf(conf={slow.confidence:.2f}<{self.min_confidence:.2f}):{slow.reason}",
            ...)
```

### ② `posture.py`:`None` 改为"保持",不再清零

```python
if upright is None:
    # "无法判定"不等于"已经坐正"
    if self._bad_streak and now - self._last_bad_ts > self.bad_hold_seconds:
        self._bad_streak = 0          # 惰性过期
    return "none"
```

- 新增 `bad_hold_seconds`(默认 60s,env `RULE_BAD_HOLD_SECONDS`):
  两帧坏帧之间允许夹"无法判定"的帧,但超过窗口没有新坏帧就视为已恢复;
- 坏帧间隔也受同一窗口约束 —— 隔了 3 分钟的两帧不算"连续"。

## 9.1 问题:第二批的 `_speed_key` 只看耗时,不看成功率

第二批把排序键改成"真实耗时优先",方向是对的,但**漏了一个维度**。上线 1 小时后
`/pool` 实测暴露:

| 后端 | real_ewma | real_samples | fail_streak |
|---|---|---|---|
| **fallback2 Sage-A1.5** | **0.33 s** | 17 | **17** |
| primary sensenova | 8.37 s | 31 | 1 |
| fallback6 Intern-S2 | 8.06 s | 18 | 1 |
| fallback10 sensenova | 8.91 s | 29 | 1 |

`fallback2` 的 **0.33 秒是"秒回错误"的耗时,不是推理耗时**。但旧排序键只看
`real_ewma`,于是它被永远排到第一位 —— 每轮并发（`AI_PARALLEL_MAX=3`）
都白占一个名额,直接拉低 quorum 达成率。

同期实测:近 2 小时慢通道 `vote1/1`（只回来 1 路）占 **34%**。

## 9.2 改法:排序键加"可靠性"档,并用熔断阈值对齐

```python
def _speed_key(self, be: "Backend") -> tuple:      # 由 staticmethod 改为实例方法
    if be.fail_streak >= self.breaker.threshold:   # 连续失败达熔断阈值
        return (3, float(be.fail_streak))          # → 一律排最后
    if be.real_samples >= 2 and be.real_ewma > 0:
        return (0, be.real_ewma)
    if be.samples >= 1 and be.latency_ewma > 0:
        return (1, be.latency_ewma)
    return (2, float("inf"))
```

- 四档由"三档"扩为"**可靠性优先**":
  `0` 健康且有真实样本 → `1` 仅探测样本 → `2` 从未测过 → `3` **近期连续失败**
- 第 3 档排到**所有**后端之后,按失败次数升序（损失最小的在前）
- 阈值取 `self.breaker.threshold`（默认 3,可配 `AI_BREAKER_THRESHOLD`),
  与熔断器同源,不会出现"熔断了但仍被优先选中"的空档
- **自愈**:`fail_streak` 在任一次成功后归零,后端恢复即自动回到第 0/1 档

三个调用点(`_pick`、`_analyze_parallel` 的 `rest.sort` / `fill.sort`)无需改动。

## 10.1 问题:`fail_streak` 降级会造成永久误杀

§9 的 P0-C 把 `fail_streak >= 熔断阈值` 的后端排到最后一档。但并发模式只取前
`parallel_max`(=3)个,而 14 个后端里通常有 8~9 个健康 —— **被降级的后端再也不会被选中**:

```
429 → fail_streak 涨到 3 → 排最后 → 永不入选
    → 永无成功机会 → fail_streak 永不归零 → 永久误杀
```

`fail_streak` 是**内存态**,只有重启才清零。而 2026-11-10 实测的 6 个 intern-ai 后端
全部返回 `HTTP 429 quota_exceeded`(见 §11),这类"额度按时段分配、会自行恢复"的失败
正好会撞上这个死锁:**额度恢复了它也回不来。**

## 10.2 改法:每个观望期放一个名额

1. `Backend` 新增 `last_fail_ts`,在 `_record_latency` 失败分支刷新;
2. `VisionPool` 新增 `probation_seconds`(默认 **900s**,env `AI_PROBATION_SECONDS`,0=关闭)
   与 `_probation_candidate()`;
3. `_analyze_parallel` 在选完 targets 后:**若观望期到点且存在候选,则用失败后端顶替最后
   一个名额**,并把 `_last_probation_ts` 推到当前时刻。

```python
cand = self._probation_candidate(avail, targets)
if cand is not None and len(targets) >= 2:
    missing = targets[-1]
    targets[-1] = cand
    self._last_probation_ts = time.time()
    log.info("probation retry: %s (fail_streak=%d idle=%.0fs, 顶替 %s)", ...)
```

**三条安全约束**:① 每个观望期只放**一个**,不会所有失败后端同时挤占并发位;
② 要求 `len(targets) >= 2`,健康后端至少保留 2 个,`quorum=2` 仍可达成;
③ `probation_seconds=0` 可整体关闭。
